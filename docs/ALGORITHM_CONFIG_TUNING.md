# 算法配置参数调优指南

## 问题回顾

**用户反馈**：
- ✅ 事件 1, 11, 12, 13 是合理的急刹车
- ❌ 事件 2, 5, 6, 7, 8, 9, 10 是误报（实际体感舒缓）
- ❌ 事件 3 和 4 是重复触发（应该是同一个事件）

**数据分析结果**：
- 误报事件的共同特征：渐进式减速（3秒），Jerk < 10 m/s³
- 当前算法只看加速度幅值，不看变化率（Jerk）
- 温和的持续减速也会被判定为急刹车

---

## 🎛️ 可通过 PocketBase 调整的参数

### 当前配置（v11）

```json
{
  "version": 11,
  "thresholdDecel": -1.6,           // 急刹车加速度阈值
  "accelDecelWindowMs": 400,         // 检测时间窗口

  "speedLowFactor": 1.1,             // 低速敏感度倍增
  "speedHighFactor": 0.9,            // 高速敏感度降低
  "couplingStrengthY": 0.5,          // Y轴抑制强度
  "turnCompMultiplier": 1.5,         // 转向补偿倍率
  "turnCompMax": 2.5                 // 转向补偿上限
}
```

## 📊 参数影响分析

### 1. **eventWindowCoverage** ⭐⭐⭐（最关键）

**当前值**: `0.6` (60%)  
**物理意义**: 400ms 窗口内，必须有多少比例的点低于阈值才触发事件

**影响分析**：
```
示例窗口（400ms @ 25Hz = 10个点）:
[-0.8, -1.0, -1.2, -1.4, -1.6, -1.7, -1.8, -1.9, -1.7, -1.5]

当前配置 (0.6):
  需要 10 × 0.6 = 6 个点 < -1.6
  实际有 5 个点 < -1.6
  → 不触发 ✅

如果改为 0.5:
  需要 10 × 0.5 = 5 个点 < -1.6
  实际有 5 个点 < -1.6
  → 触发 ❌ (会增加误报)

如果改为 0.8:
  需要 10 × 0.8 = 8 个点 < -1.6
  实际有 5 个点 < -1.6
  → 不触发 ✅ (会减少误报)
```

**建议值**: `0.75 - 0.85`

**原理**：
- 真正的急刹车：加速度会在短时间内**持续**低于阈值（80%+ 的点）
- 温和减速：加速度渐进变化，只有部分点低于阈值（40-60%）

**预期效果**：
- ✅ 减少误报：温和减速不再触发
- ⚠️ 可能漏报：如果急刹车后有反弹（松刹车），可能不触发

---

### 2. **thresholdDecel** ⭐⭐

**当前值**: `-1.6` m/s²  
**物理意义**: 判定为"急刹车"的加速度阈值

**影响分析**：
```
观察到的加速度范围：
- 温和减速: -1.2 ~ -1.8 m/s²
- 中等刹车: -2.0 ~ -2.5 m/s²
- 急刹车:   -2.5 ~ -4.0 m/s²

当前阈值 -1.6:
  温和减速的峰值 (-1.8) 已经超过阈值
  → 容易误报 ❌

如果改为 -2.0:
  温和减速的峰值 (-1.8) 不会超过阈值
  → 减少误报 ✅
  
如果改为 -2.5:
  只有真正的急刹车才会触发
  → 大幅减少误报，但可能漏报 ⚠️
```

**建议值**: `-2.0` 或 `-2.2`

**原理**：
- 1G = 9.81 m/s²
- -2.0 m/s² ≈ 0.2G 的减速度
- 这是一个温和但明确的刹车动作

**预期效果**：
- ✅ 大幅减少误报
- ⚠️ 可能漏掉一些"轻度急刹车"

---

### 3. **accelDecelWindowMs** ⭐

**当前值**: `400` ms  
**物理意义**: 检测急刹车的时间窗口大小

**影响分析**：
```
真正的急刹车：
  踩刹车动作时间: 0.2-0.5秒
  加速度峰值持续: 0.3-0.6秒
  
温和减速：
  持续时间: 2-5秒
  加速度缓慢变化

400ms 窗口：
  ✅ 能捕获急刹车的峰值
  ❌ 也会捕获温和减速的片段

200ms 窗口：
  ✅ 只捕获真正的峰值
  ⚠️ 可能对采样率敏感（25Hz下只有5个点）

600ms 窗口：
  ❌ 更容易包含温和减速的片段
```

**建议值**: 保持 `400` 或改为 `300`

**原理**：
- 窗口太小：容易漏报，对噪声敏感
- 窗口太大：容易误报，混入非事件数据

**预期效果**：
- 改为 300ms：略微提高准确性，但影响有限

---

### 4. **speedLowFactor / speedHighFactor** ⭐

**当前值**: 
- `speedLowFactor: 1.1` (低速时阈值放宽 10%)
- `speedHighFactor: 0.9` (高速时阈值收紧 10%)

**影响分析**：
```
事件2速度: 22 km/h (低速)
  实际阈值 = -1.6 × 1.1 = -1.76
  → 更容易触发（因为低速时动作更明显）
  
事件12速度: 83 km/h (高速)
  实际阈值 = -1.6 × 0.9 = -1.44
  → 更敏感（因为高速刹车危险性更大）
```

**建议值**: 
- `speedLowFactor: 1.0` (取消低速放宽)
- `speedHighFactor: 0.85` (高速更敏感)

**原理**：
- 低速下的"急刹车"通常不需要特别关注
- 高速下的任何异常减速都应该记录

---

### 5. **couplingStrengthY** ⭐

**当前值**: `0.5`  
**物理意义**: Z轴（垂直）干扰对Y轴（前后）检测的抑制强度

**影响分析**：
```
颠簸路段：
  Z轴活动大 (> 2.5 m/s²)
  → Y轴检测阈值提高
  → 防止颠簸误报为急刹车 ✅

平坦路段：
  Z轴活动小
  → Y轴检测正常
```

**建议值**: 保持 `0.5`

**原理**：这个参数主要防止颠簸路段的误报，与当前问题关系不大

## ⚠️ 局限性说明

### 只调参数**无法完全解决**的问题：

1. **渐进式减速 vs 急刹车**
   - 两者加速度峰值可能相同
   - **根本区别在于 Jerk（加速度变化率）**
   - 当前算法不看 Jerk，只调阈值治标不治本

2. **事件 3 和 4 的重复触发**
   - 间隔 3.2 秒，大于默认防抖 2 秒
   - **需要修改代码**中的防抖逻辑
   - 配置中没有防抖时间参数

3. **长期优化**
   - 建议在配置中增加 `minJerkThreshold` 参数
   - 在代码中实现 Jerk 判断逻辑
   - 这样可以通过配置灵活调整
