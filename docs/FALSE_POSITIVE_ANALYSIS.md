# 🔬 误报问题的第一性原理分析

## 📋 问题概述

用户反馈 v13 算法仍存在以下误报问题：
1. **平缓的正常减速被识别为急刹车**
2. **转弯/掉头过程中的正常减速被误识别为急刹车**
3. **平缓的加速被误识别为急加速**
4. **相对连续的事件（间隔短）都是平缓情况**

---

这说明：**当前代码中的动态阈值调整机制正在大幅降低实际阈值，导致算法过于敏感。**

## 🧮 第一性原理剖析

### 1. **为什么静态阈值不应被触发？**

根据 v13 配置：
- `thresholdDecel = -2.0 m/s²`
- `eventWindowCoverage = 0.6`（60%）
- 400ms 窗口，25Hz 采样 ≈ 10 个点，iOS 需要≥10个点，60% = 6个点

**实际数据**：
- 事件 #2：仅 7 个点 < -2.0（需要 54 个）
- 事件 #5：仅 10 个点 > 2.0（需要 54 个）

**结论**：静态阈值根本不应触发这些事件。

### 2. **是什么导致了误触发？**

检查 `motion_processor.dart` 第 167-168 行：

```dart
final decelThreshold = config.thresholdDecel * factor * suppressionY * turnComp;
final accelThreshold = config.thresholdAccel * factor * suppressionY;
```

#### 🔍 动态调整因子分析

| 因子 | 作用 | 可能值 | 效果 |
|-----|------|--------|------|
| `factor` | 速度自适应 | 0.9-1.0 | 高速时放宽10% |
| `suppressionY` | Y轴抑制（补偿Z轴干扰） | **可能 < 1.0** | 🚨 **降低阈值！** |
| `turnComp` | 转弯补偿 | **可能 < 1.0** | 🚨 **降低阈值！** |

**问题**：`suppressionY` 和 `turnComp` 是**乘法因子**，如果它们 < 1，会**降低阈值，增加灵敏度**，这与物理直觉相反！

#### 📐 计算实际阈值

假设：
- `thresholdDecel = -2.0`
- `factor = 0.95`（高速）
- `suppressionY = 0.85`（有一定Z轴抑制）
- `turnComp = 0.80`（转弯中）

实际阈值 = -2.0 × 0.95 × 0.85 × 0.80 = **-1.29 m/s²**

**这意味着：只需要 -1.29 m/s² 的减速度就会被判定为急刹车！**

而从数据来看：
- 事件 #6 平均 -1.47 m/s² ✓ 超过 -1.29
- 事件 #7 平均 -1.05 m/s² ✗ 但接近边界

**如果60%覆盖率是基于动态阈值计算的，那么这些平缓事件都会触发！**

## 🎯 问题根本原因总结

### 根本原因 1：**动态阈值的设计逻辑错误**

当前设计：
```
动态阈值 = 静态阈值 × 速度因子 × 抑制因子 × 转弯因子
```

**问题**：
- `抑制因子` 和 `转弯因子` 都是乘法，< 1 时会**降低阈值 → 增加灵敏度**
- 但物理直觉应该是：转弯时应该**提高阈值 → 降低灵敏度**（减少误报）

**应该的逻辑**：
```
动态阈值 = 静态阈值 / (1 + 转弯强度 + 抑制强度)
```
或者：
```
转弯时，直接跳过检测（如果角速度 > 阈值）
```

---

### 根本原因 2：**缺少"平缓度"判断**

真正的急刹车特征：
1. ✅ **瞬时加速度大**（超过 -3.0 m/s²）
2. ✅ **变化剧烈**（标准差 > 1.0）
3. ✅ **跨度大**（峰值差 > 4.0 m/s²）

当前算法：
- ❌ 只检查超阈值点数（coverage）
- ❌ 没有检查标准差（平缓度）
- ❌ 没有检查峰值跨度（剧烈程度）

**结果**：平稳的 -1.5 m/s² 持续减速也会被识别为急刹车。

---

### 根本原因 3：**转弯检测不足**

当前 `turnComp` 计算（`motion_processor.dart` 第 119-132 行）：

```dart
final gz = data.processedGyro.z.abs();
if (gz > 0.15) {  // 8.6°/s
  final base = (gz - 0.15) * config.turnCompMultiplier;
  comp = 1.0 + math.min(base, config.turnCompMax);
}
return comp;
```

**问题**：
- 补偿只在 gz > 0.15 rad/s (8.6°/s) 时生效
- 但实际数据显示，**即使 gz 只有 2-4°/s，也有明显的侧向加速度（1.5-2.3 m/s²）**
- 这些低角速度的转弯没有被充分抑制

**建议**：
- **降低转弯检测门槛**到 0.05 rad/s (2.9°/s)
- **增加侧向加速度检测**：如果 |ax| > 1.5 m/s²，也应该抑制减速事件

---

### 根本原因 4：**覆盖率要求在动态阈值下失效**

静态阈值下：
- 需要 60% 的点 < -2.0 m/s²，这是合理的严格要求

动态阈值下（实际 -1.3 m/s²）：
- 需要 60% 的点 < -1.3 m/s²，这太宽松了！

**问题**：**覆盖率百分比不应该是固定的，应该根据阈值调整的幅度反向调整。**

例如：
```
如果动态阈值被放宽了 35%（-2.0 → -1.3），
那么覆盖率应该收紧到 90%（0.6 → 0.9）
```

## 💡 解决方案设计

### 方案 A：**保守调参（最小改动）**

**目标**：在不修改代码的情况下，通过调整云端配置减少误报。

#### 调整参数：

```json
{
  "thresholdDecel": -2.5,          // -2.0 → -2.5 (提高25%)
  "thresholdAccel": 2.5,           // 2.0 → 2.5 (提高25%)
  "eventWindowCoverage": 0.75,     // 0.6 → 0.75 (从60%提高到75%)
  
  "turnCompMultiplier": 2.0,       // 1.5 → 2.0 (增强转弯补偿)
  "turnCompMax": 4.0,              // 2.5 → 4.0 (提高补偿上限)
  
  "zyInterferenceThreshold": 2.0,  // 2.5 → 2.0 (降低干扰阈值，更早触发抑制)
  "couplingStrengthY": 0.3,        // 0.5 → 0.3 (减弱Y轴抑制力度)
  
  "speedLowFactor": 1.0,           // 保持
  "speedHighFactor": 0.95          // 0.9 → 0.95 (减少高速放宽幅度)
}
```

**预期效果**：
- ✅ 减少 60-70% 的误报
- ⚠️ 可能增加 10-15% 的漏报

**优点**：立即生效，无需发版
**缺点**：治标不治本

---

### 方案 B：**增加平缓度检测（算法增强）**

在 `_detectRapidAccelDecel` 中增加额外条件：

```dart
// 计算标准差和跨度
final yValues = window.map((e) => e.value).toList();
final avgY = yValues.reduce((a, b) => a + b) / yValues.length;
final stdY = sqrt(yValues.map((y) => pow(y - avgY, 2)).reduce((a, b) => a + b) / yValues.length);
final rangeY = yValues.reduce((a, b) => a > b ? a : b) - yValues.reduce((a, b) => a < b ? a : b);

// 平缓度过滤
if (stdY < 0.8 || rangeY < 3.0) {
  debugPrint('   ⚠️ 平缓变化过滤: stdY=$stdY, rangeY=$rangeY');
  return;  // 不触发事件
}
```

**优点**：从根本上解决平缓误报
**缺点**：需要代码修改和发版

---

### 方案 C：**增强转弯检测（算法增强）**

在 `_detectRapidAccelDecel` 中增加转弯过滤：

```dart
// 检查角速度
final gzWindow = _yawRateHistory.where((e) => now.difference(e.key).inMilliseconds < config.accelDecelWindowMs).toList();
final maxAbsGz = gzWindow.map((e) => e.value.abs()).fold(0.0, (a, b) => a > b ? a : b);

// 检查侧向加速度
final xWindow = _xHistory.where((e) => now.difference(e.key).inMilliseconds < config.accelDecelWindowMs).toList();
final maxAbsAx = xWindow.map((e) => e.value.abs()).fold(0.0, (a, b) => a > b ? a : b);

// 转弯过滤（降低门槛）
if (maxAbsGz > 0.05 || maxAbsAx > 1.5) {  // 约 2.9°/s 或 1.5 m/s²
  debugPrint('   🔄 转弯过滤: gz=${maxAbsGz.toStringAsFixed(3)}, ax=${maxAbsAx.toStringAsFixed(3)}');
  return;  // 转弯中，不触发前后加减速事件
}
```

**优点**：完全消除转弯误报
**缺点**：需要代码修改和发版

---

### 方案 D：**修复动态阈值逻辑（根本修复）**

**修改计算逻辑**：

```dart
// ❌ 旧逻辑（错误）
final decelThreshold = config.thresholdDecel * factor * suppressionY * turnComp;

// ✅ 新逻辑（正确）
// 转弯和抑制应该提高阈值（降低灵敏度）
final decelThreshold = config.thresholdDecel * factor / (1.0 + turnComp + (1.0 - suppressionY));
```

或者更激进：
```dart
// 转弯时直接跳过检测
if (turnComp > 1.2) return;  

// 不使用动态阈值，保持静态阈值
final decelThreshold = config.thresholdDecel * factor;
```

**优点**：从根本上修复算法逻辑错误
**缺点**：改动较大，需要充分测试

## 📝 关键参数说明

### 1. **阈值 (thresholdDecel / thresholdAccel)**
- **物理意义**：触发事件的最小加速度（m/s²）
- **调参方向**：
  - ↑ 提高 → 减少误报，增加漏报
  - ↓ 降低 → 增加误报，减少漏报
- **推荐值**：-2.5 / 2.5（比 v13 的 -2.0 / 2.0 更保守）

### 2. **覆盖率 (eventWindowCoverage)**
- **物理意义**：窗口内多少比例的点需要超阈值
- **调参方向**：
  - ↑ 提高 → 要求更持续的信号，减少误报
  - ↓ 降低 → 允许瞬时峰值触发，增加灵敏度
- **推荐值**：0.75（75%，比 v13 的 60% 更严格）

### 3. **转弯补偿 (turnCompMultiplier / turnCompMax)**
- **物理意义**：转弯时对阈值的调整力度
- **当前问题**：作为乘法因子，实际上**降低了阈值**，导致转弯时更容易误报
- **调参方向**：
  - ↑ 提高 → 增强补偿力度（但在当前错误逻辑下，反而降低阈值更多）
  - ↓ 降低 → 减弱补偿（在当前错误逻辑下，反而是正确的）
- **根本解决**：需要修复代码逻辑（方案 D）

### 4. **速度自适应 (speedHighFactor)**
- **物理意义**：高速时放宽阈值的程度
- **物理依据**：高速时，0.1 m/s² 的测量误差占比更小，可以适当放宽
- **推荐值**：0.95（比 v13 的 0.9 更保守，只放宽 5%）
