## ⚠️ 关键发现

### 1. **检测窗口的尴尬现象**

你的传感器数据片段（sensor_fragment）是 **3 秒**（91 个点 @ 25Hz），但检测窗口只有 **350ms**（约 9 个点）。

**问题**：
```
实际情况：
- 传感器保存了 3 秒数据（完整的刹车过程）
- 但只用前 350ms 的数据来判断是否触发

结果：
- 渐进式刹车：前 350ms 加速度还不够大 → 不触发 ✅
- 急刹车：前 350ms 就有明显峰值 → 触发 ✅
```

**这其实是好事**！350ms 的窗口正好能区分"瞬时动作"和"渐进过程"。

---

### 2. **eventWindowCoverage 的影响**

**当前要求**：350ms 窗口（约 9 个点）中，需要 **75%**（7 个点）低于阈值。

```
示例分析（事件 4，真正的急刹车）:
  峰值: -3.247 m/s²
  350ms 窗口: 假设有 9 个点
  低于 -2.0 的点数: 约 3-4 个
  
  v11 (60%): 需要 5.4 个点 → 不触发 ❌
  v13 (75%): 需要 6.75 个点 → 不触发 ❌
```

**问题在于**：即使是真正的急刹车（峰值 -3.2），在 350ms 短窗口内也只有少数几个点达到峰值！

## 🔥 核心矛盾

### 矛盾点：窗口太短 vs 覆盖率太高

```
accelDecelWindowMs: 350ms   ← 窗口短，好处是精确
eventWindowCoverage: 0.75   ← 覆盖率高，要求严格

结合效果：
  急刹车的瞬间峰值通常只持续 100-200ms
  在 350ms 窗口中，峰值点可能只占 30-50%
  
  → 要求 75% 的覆盖率太高了！
```

### 真实世界的急刹车特征：

```
Time: 0ms -------- 100ms -------- 200ms -------- 300ms -------- 400ms
Accel: -0.5 → -1.2 → -2.8(峰值) → -2.5 → -1.8 → -1.0

在这个例子中：
  低于 -2.0 的点: 约 150ms（42% 的时间）
  v11 (60% 在 400ms): 需要 240ms → 不触发 ❌
  v13 (75% 在 350ms): 需要 262ms → 不触发 ❌
```

## 📈 参数调优指南

### eventWindowCoverage 的物理意义

```
覆盖率 = (低于阈值的点数) / (窗口总点数)

实际含义：急刹车的"纯度"

60%: 峰值持续时间占窗口的 60%
     → 适合捕获有明显峰值的急刹车
     
75%: 峰值持续时间占窗口的 75%
     → 只能捕获峰值极其明显且持续的急刹车
     → 很容易漏报
     
50%: 峰值持续时间占窗口的 50%
     → 太宽松，会误报
```

### 窗口时间的选择

```
200ms: 只看峰值瞬间
  ✅ 最精确
  ❌ 对采样率敏感，容易受噪声影响
  
350ms: 看峰值 + 部分上升/下降
  ✅ 较精确
  ⚠️  需要配合低覆盖率 (0.5-0.6)
  
450ms: 看完整的峰值过程
  ✅ 平衡
  ✅ 配合中等覆盖率 (0.6-0.65)
  
600ms: 看峰值 + 前后变化
  ⚠️  可能混入非事件数据
  ✅ 配合高覆盖率 (0.7-0.75)
```
